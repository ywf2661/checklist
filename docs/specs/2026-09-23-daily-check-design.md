# 일일 시스템 점검 웹 체크리스트 — 설계서 (v2)

- 작성일: 2026-09-23 (v2: 2026-09-24, 종이 점검표 구조 반영)
- 상태: 사용자 검토 대기

## 1. 목적

IT 부서원이 매일 아침 담당 항목을 점검할 때 쓰는 종이 체크리스트를 웹으로 대체한다.
점검 기록은 감사·내부통제 증적으로 쓰이므로 위변조 방지와 이력 보존이 필요하다.

**성공 기준**
- 부서원이 종이 없이 자기 담당 항목의 이상 유/무와 비고를 입력·제출한다.
- 팀장이 한 화면에서 미제출 항목·이상 항목·담당자별 진행률을 보고 하루치를 확인(결재)한다.
- 특정 날짜의 점검 기록을 종이와 같은 표로 인쇄/PDF, CSV로 제출할 수 있다.

## 2. 제약 / 결정 사항

| 항목 | 결정 |
|---|---|
| 운영 환경 | 사내 서버 직접 설치, 외부 인터넷 없음 |
| 기술 스택 | Python 3 + Flask + SQLite(표준 `sqlite3`) + waitress |
| 외부 패키지 | `flask`, `waitress` 2개만 |
| 화면 | 서버 렌더링(Jinja2), JS 프레임워크·외부 폰트 없음, 네이비 금융형 디자인 |
| 로그인 | 앱 자체 ID/비밀번호, 해시 저장, 5회 실패 잠금, 첫 로그인 시 비밀번호 변경 |
| 엑셀 출력 | CSV(UTF-8 BOM, 수식 삽입 방지) |
| PDF 출력 | 인쇄용 CSS + 브라우저 "PDF로 저장" |
| 백업 | `python app.py backup <폴더>` (SQLite 온라인 백업) |

## 3. 역할

| 역할 | 권한 |
|---|---|
| member (부서원) | 점검 입력·제출·수정(사유), 항목 관리, 이력 조회 |
| leader (팀장) | member 권한 + 현황판, 하루치 확인. 팀장은 점검하지 않는다 |
| admin (관리자) | leader 권한 + 사용자 관리 |

## 4. 점검 항목 구조

종이 점검표의 번호로 계층을 표현한다.

| 번호 | 항목명 | 종류 | 담당자 |
|---|---|---|---|
| 1 | 네트워크 및 시스템 점검 | 구분 | - |
| 1-1 | 네트워크상태 | 구분 | - |
| 1-1-1 | 백본 및 각 층 네트워크 상태 | 점검 | 김대리 |

- 번호 형식: 숫자를 `-`로 이은 것(`1`, `1-1`, `1-1-1`). 끝의 `.`은 무시. 번호는 유일.
- 정렬: 번호를 숫자 단위로 비교(`1-2` < `1-10`). 들여쓰기 = `-` 개수.
- 종류: **구분**(제목줄, 입력 없음) / **점검**(담당자 1명, 이상 유/무·비고 입력).
- 미사용 처리만 가능, 삭제 없음. 모든 변경은 감사로그.
- **항목 관리 화면은 모든 사용자**가 쓴다(추가·수정·미사용). 사용자 계정 관리는 관리자만.
- **일괄 등록**: 한 줄에 `번호 | 항목명 | 담당자ID` (담당자 비우면 구분). 한 줄이라도 오류면 전체 취소하고 오류 줄을 알려준다.

## 5. 화면

1. **로그인 / 비밀번호 변경**
2. **오늘 점검** (`/`) — 번호순 표. 구분 줄은 제목으로, 점검 줄은
   `번호 · 항목명 · 담당자 · 이상 ○무 ○유 · 비고 · 상태`.
   - 보기 전환: **내 항목**(기본) / **전체**(남의 항목도 대신 입력 가능, 대무).
   - 상단에 내 진행률(`내 항목 3/8 제출`).
   - 버튼: 임시저장 / 제출. 제출은 **이상 유/무를 고른 줄만** 제출하고, 결과를 "N건 제출, 남은 내 항목 M건"으로 알려준다.
   - 제출된 줄은 잠김. 줄마다 "수정" → 그 줄만 편집 + 수정 사유 입력.
   - 오늘 날짜만 새로 입력 가능. 과거 날짜는 `/?day=YYYY-MM-DD`로 조회만(제출된 줄의 사유 수정은 가능).
3. **현황판(팀장)** — 날짜 선택. 타일: 전체 점검항목 / 미제출 / 이상 유 / 확인 상태.
   담당자별 진행률 표, 이상 유 항목 목록, 미제출 항목 목록. **하루치 확인** 버튼.
4. **이력 조회** — 기간별 하루 요약(날짜, 제출/전체, 이상 건수, 확인자). 날짜 클릭 → 그날 전체 표.
   인쇄/PDF(종이와 같은 표 + 확인자 칸), CSV(항목 1줄 = 1행).
5. **항목 관리** — 번호순 표에서 줄별 수정(번호·항목명·종류·담당자·사용), 한 줄 추가, 일괄 등록.
6. **관리(관리자)** — 사용자 추가·역할·비밀번호 초기화·잠금 해제·미사용.

## 6. 데이터 모델

```sql
users(id, login_id UNIQUE, name, pw_hash, role, fail_count, must_change_pw, active)
items(id, code UNIQUE, title, is_group, owner_id, active)
results(id, date, item_id, code, title, owner_name,      -- 번호·항목명·담당자명은 저장 시점 스냅샷
        checker_id, issue, remark, status, submitted_at,  -- issue: NULL(미선택)/0(무)/1(유)
        UNIQUE(date, item_id))                            -- status: draft | submitted
days(date PRIMARY KEY, approved_by, approved_at)
audit_log(id, at, user_id, target, target_id, action, before, after, reason)  -- 추가만 가능(트리거)
```

## 7. 증적 규칙

1. 제출된 줄은 잠김. 수정은 사유 필수, 변경 전/후를 `audit_log`에 기록.
2. 이상 "유"면 비고 필수. 이상 유/무는 기본값 없음(직접 선택).
3. 하루치 확인은 그날 사용 중인 모든 점검항목이 제출돼야 가능. 확인자는 그날 본인이 제출한 항목이 없어야 한다.
4. 확인 후 그날 항목이 수정되면 확인이 풀리고 감사로그에 남는다.
5. 제출 시 번호·항목명·담당자명을 `results`에 복사해 두어, 이후 항목 변경이 과거 기록을 바꾸지 않는다.
6. 삭제 기능 없음. 사용자·항목은 미사용 처리만.
7. 화면을 연 뒤 다른 사람이 같은 줄을 먼저 저장·제출했으면, 저장을 거부하고 새로고침을 안내한다(조용한 덮어쓰기 금지).
8. 시각은 서버 시간 기준.
9. 항목은 추가한 날부터 미사용 처리한 날 전까지만 그날의 점검 대상이다. 나중에 항목을 추가·미사용 처리해도 지난 날짜의 대상 목록과 확인 가능 여부는 바뀌지 않는다.
10. 점검 기록이 있는 항목은 종류(구분/점검)를 바꿀 수 없다. 확인 후 그날 새로 제출·수정하면 확인이 풀린다. 그날 항목을 제출하거나 수정한 사람은 그날을 확인할 수 없다.

## 8. 보안

- 비밀번호 해시 저장, 세션 쿠키 `HttpOnly`·`SameSite=Lax`, 모든 POST에 CSRF 토큰.
- 모든 SQL은 파라미터 바인딩. 역할 검사는 서버에서 라우트마다.
- 미사용 처리한 사용자는 기존 세션도 즉시 차단.
